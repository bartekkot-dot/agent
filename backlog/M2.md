## Step 2 — merge content.ts (don't blindly overwrite)

Adopt the addendum's shape (`APP_NAME` / `DOWNLOAD_URL` / `REPO_URL` top-level consts +
the `content` object with `nav`, `hero`, `councilDemo`, `models`, `council`, `research`,
`privacy`, `stats`, `download`, `footer` keys) as the target structure, but:

- **Keep the real GitHub wiring, don't regress to the addendum's placeholder.** The
  addendum's `DOWNLOAD_URL = ".../OWNER/REPO/..."` is a stand-in the spec itself marks
  TODO. The current site already has a real, working release-fetch flow:
  `content.github = {owner: "tomaszrymaszewski", repo: "ChatUI-local"}`,
  `content.links = {releases, allReleases, source}`, consumed by
  `src/hooks/use-latest-release.ts` → `src/lib/github-releases.ts`
  (`fetchLatestRelease`/`matchAssetForOS`) inside `download-section.tsx`. Keep `github` and
  `links` in the merged content.ts exactly as they are now, and keep that fetch flow
  wholesale — it already does per-OS asset matching, which is strictly better than a
  static href.
  - Concretely: `download.primary` in the merged file should NOT be
    `{label, href: DOWNLOAD_URL}` — keep `download-section.tsx`'s existing dynamic
    button logic (loading / matched-asset / fallback states), just re-skin its copy
    (`headline`, `sub`, `secondary` "Build from source" → `content.links.source`) from
    the addendum's `download` key.
  - Concretely: `hero.primary` should link to `#download` (scroll-to, matching the
    current hero's existing pattern), not directly to `DOWNLOAD_URL` — the real
    OS-specific button lives in the download section; don't duplicate/fork that logic
    into the hero. Adjust the button label accordingly (e.g. just "Download", since it
    can't know the OS before scrolling) — use judgment, but don't claim "for Mac" in the
    hero if the visitor might be on Windows/Linux.
- **Adopt the addendum's flatter naming** (`APP_NAME` const instead of nested
  `content.app.name`) since that's what the spec's file literally uses — update
  `site-header.tsx` (`content.app.name` → `APP_NAME`, `about-section.tsx` is dead code so
  ignore it) and `site-footer.tsx` (`content.app.name` → `APP_NAME`) accordingly.
- **Rename `privacy.heading`/`privacy.lead`** to the addendum's `privacy.headline`/
  `privacy.sub` (matches the naming convention every other new section key uses —
  `headline`/`sub` — for consistency across the file). Update `privacy-section.tsx`'s
  reads accordingly.
- **Drop** `app.tagline`, `app.slogan`, `app.blurb`, `showcase[]`, `integrations[]`,
  `features[]`, `faq[]`, `value` — superseded by the new keys / removed sections (see
  Step 3). Don't leave orphaned keys nothing reads.
- **Stats are placeholder values** (`"8+" Providers supported`, `"MIT" Open source`) —
  the spec itself marks these TODO. **Ask the user to confirm the real provider count and
  license before wiring this section up** with those numbers; if unconfirmed by the time
  you reach this step, use the two numbers that are self-evidently true without asking
  (`"100%" On your device`, `"0" Servers`) and leave the other two out rather than ship an
  unconfirmed number — G6 in `PLAN.md` ("no fabricated assets") extends to fabricated
  stats.
- `councilDemo` (model IDs, streamed lines, synthesis) — copy it into content.ts as-is,
  but you don't need to *use* it yet in this item (M3/M4 consume it). Just make sure it's
  present so M3/M4 don't also need to touch content.ts.
